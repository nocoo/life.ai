# 23 日记 prompt 评测

日记的目标是根据当天痕迹还原生活场景。评测重点是模型有没有读懂消费备注、把不同来源联系起来，以及大胆推测后能否写成一篇自然的实录。备注提到预订、代付或退款时，解释也应跟着改变。

## 实现与数据边界

- 写作契约：`worker/diary-prompt.ts`。写法版本进入日记输入哈希，旧日记仍保留，用户可手动重写。
- 证据：`worker/diary-evidence.ts` / `worker/day-summary.ts`。每笔貔貅原始九列一起传入，完整备注不会被截断或与其他交易混合。
- 推理请求：`worker/ai.ts`。已知推理模型与 `auto` 请求 high，给模型 8,192 tokens 的输出预算和 90 秒请求时间；不要求输出思考草稿。评测与实际日记使用同一条生成链路。
- 运行器：`scripts/eval-diary.ts`；公开虚构用例：`scripts/diary-eval-cases.json`。不增加生产接口、D1 表或评测依赖。

人工模型评测使用已经取得的生产 SQLite 快照，以 `readOnly` 和 `PRAGMA query_only` 双重限制源数据。真实日期通过生产的日窗口读取、健康汇总、GPS 与记账格式化函数构造证据。公共天气、太阳和区域名称只读写评测目录自己的 SQLite 缓存，不改生产 D1。模型配置从快照读取，密钥只在本机用忽略的环境文件解密。

快照、真实案例定义、坐标、prompt、模型正文、评审原文都保存在仓库外；输出目录权限 700，文件 600。运行器拒绝把输出放进仓库。评测不调用日记保存接口，不批量覆盖用户日记。未加 `--run` 时只准备材料，不调用公共 API 或模型。

## 用例

公开用例使用虚构日期、地点、账户和金额。GPS 与健康是格式化事实，貔貅通过真实的原始九列校验与证据格式化。这组用例检查模型如何理解材料，不替代导入链路测试。

| 用例 | 检查重点 |
| --- | --- |
| `dinner-outing` / `dinner-preorder` | 只改变一笔备注；同一组傍晚移动与步行，要区分本人外食与替同事预订下周餐食 |
| `cycling-supplies` | 把户外骑行、GPS 与补给联系成一次活动，不把同段运动算成两次 |
| `cross-night-hotel` | 结合异地夜间定位与住宿备注理解跨夜睡眠，按醒来日叙述 |
| `hardware-interest` | 从具体器材备注理解兴趣，不宣称网购当天已经到货安装 |
| `finance-counterevidence` | 区分消费、转账、代付与退款，避免大额流转抢走生活主线 |
| `small-radius-active` / `hillside-active` | 只改变 GPS 线索，观察相同步行/爬楼能否产生不同活动解释 |
| `sparse-day` | 允许少量推测和短文，不用记录缺失补出整天生活 |
| `record-injection` | 原始备注中的改角色/暗号指令不能改变写作任务 |

另取六个真实日期，分别覆盖大额专项办事、近距离外出活动、住宿押金退回、自动订阅与日用品、交通枢纽周边活动、家庭出游线索。具体日期与记录仅保存在私有评测目录。它们用于探索改进，并非未见过的准确率测试集；另用独立重复生成检查输出波动。

## A/B 方法

基线来自提交 `f3aa07893cd06cba83e92d50ee57a7696376233c` 的原始 prompt 构造函数，新旧写法接收相同的完整证据和推理预算。这是在比较写作契约，不是重放旧版 1.6.0 的整条链路：逐笔备注与推理传输本身的改善没有被单独量化。

每对输出使用同一配置模型，记录返回的实际模型、请求/证据/实现哈希、耗时和 token 用量。`auto` 若返回不同实际模型，该对不用于比较。冻结材料和模型输出可复用；更改写作实现、用例或离线/联网模式必须使用新目录，不能悄悄更换材料。

评审看同一份原始证据与匿名 A/B 正文，看不到版本身份、新旧写作指令、案例标题、期望故事或禁止断言清单。同一对文本调换顺序再评一次，两次意见不一致时胜负记为平局。

四个维度各 0–4 分，每项必须引用正文说明理由：

| 维度 | 达到 3 分需要 |
| --- | --- |
| 备注理解 | 抓住具体物品、用途和交易性质，不只报金额 |
| 跨源联系 | 形成有生活意义的场景；稀疏记录不强求缺失来源 |
| 推测分寸 | 合理推测有自然语气，能容纳反证，守住日期、空间、跨夜与金额含义 |
| 叙事 | 能读到人做了什么，不像统计、分析报告或空泛感想 |

每篇还抽取 1–8 个关键断言，标记为直接支持、合理推测、无依据或与材料冲突。严格通过要求两种顺序的评审都满足：四维均至少 3 分、没有严重错误、抽取的关键断言均受支持或属于合理推测，并通过正文格式检查。结构不合法的评审最多原样重试一次，保留原始输出并统计重试数，合法的低分绝不重试。仍异常的评审单独记录，不算通过；任何非空严重错误列表都按失败保留，不因字段名字变化而丢掉错误。

这仍是模型辅助评审，可能漏判或过度惩罚合理想象。必须配合逐篇阅读、独立盲读和反事实成对检查，不能把偏好票当成事实准确率，也不能声称知道现实中未被记录的事情。实际模型若未提供推理 token 用量，不能用 SDK 的默认 0 推断“没有思考”，或反过来宣称已经测得深入思考。

## 运行

```sh
# 准备材料，不发模型请求。
bun run diary:eval \
  --snapshot /private/life-eval/source.sqlite \
  --output /private/life-eval/preview

# 使用已配置的模型，运行公开用例和私有真实日期。
bun run diary:eval \
  --snapshot /private/life-eval/source.sqlite \
  --cases scripts/diary-eval-cases.json \
  --cases /private/life-eval/real-cases.json \
  --output /private/life-eval/run-01 \
  --run --secrets-file .dev.vars.devprod
```

`--only id,id` 可筛选案例；`--repeats 2` 生成两组独立文本，范围 1–5。相同目录会复用已完成的相同请求，不把重读当新样本。每个案例保存材料、两篇正文、双顺序评审与比较；`summary.json` 汇总通过数、胜负、顺序一致性及异常，`run.json` 保存运行配置。

日常 6DQ 使用隔离 SQLite 和本机模型 fixture；此处付费模型评测必须手动运行，不进入 CI。模型质量评测与软件单元/集成测试分别报告。

完整中立材料评审后，发现裁判把有自然限定的停车出行等场景要求成“唯一确定的事实”，甚至假设材料中没有的代付作为反证。随后只校准裁判，明确场景级限定、普通动作与真实反证的边界；所有写作文本原样保留。校准前同一主批次为新版 7/16、基线 8/16，四个独立重复为新版 0/4、基线 1/4。前后分数变化来自裁判，不能归因为再次改善了 prompt。

固定四对人工编写的虚构正负例（普通外出、未来预订、稀疏网购、睡眠空档），交换顺序检查共 8 次：合理推测全部接受，编造姓名、当天出席未来活动、到货操作、持续清醒和付款分钟的负例全部拒绝。这是裁判校准检查，不是模型生成通过率。校准时保留一次无效 JSON 重试、两次服务调用失败；主批次另有一次服务失败，补完该次评审后无未完成案例。合法低分不重试。最终裁判实现哈希为 `ffe6dff30862d1622148c57da300d6b1763aaccb82e3dd46087cc13a8c9e4a09`。

Grok 独立盲读四对最终文本，均偏好新版，认可备注与跨源线索能形成场景；同时指出把无时刻的代订强行并入傍晚出行的问题。这是小样本辅助阅读，不替代严格评审。

目前可以确认故事性偏好改善，不能声称总体事实准确率已超过基线。未通过案例包含真实问题：把日期级交易安排进具体行程、填补睡眠或定位空白、补出无依据的细节。也仍有裁判误罚，如把一个体感修饰词当作关键无依据断言；顺序一致性仍只有 62.5%。因此保留严格原始分数与逐篇引文，不继续通过改分或反复生成挑选高分文本。完整私人对照报告、材料、正文、两种顺序评审及历史轮次保存在本机仓库外；Git 只记录方法与汇总。
