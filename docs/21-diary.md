# 每日日记

当日 AI 摘要是一篇根据个人痕迹还原生活场景的实录。模型先代入当天的主人，理解消费、移动与身体活动之间的联系，再以“你”为主语写给用户。仍由用户手动生成，保存在 D1 `day_summaries`，全来源入账，不受页面筛选影响。

## 证据

生成时收集：

- 天气与日出日落（`worker/public-context.ts`：`getDayWeather` / `getDaySun`，按代表停留点查询）。任一提供者失败只省略该段，其余证据照常写入
- 健康：跨夜睡眠按起床日，保留卧床／实际睡眠／清醒／阶段的区别，并提供今晚入睡。小时步行、爬楼、心率峰值与锻炼起止形成身体活动的时间线；重复锻炼只用 canonical 记录。血氧、呼吸、HRV、静息心率标明是当日观测或样本汇总，不能配上虚构的时刻；心电图、血压保留测量时间与各自单位
- 全部健康 Record 维度另按原类型与单位汇总条数、数值范围和首末观测，避免低频体重、VO₂ max、腕温、噪声提醒等被高频样本挤掉。这些原始范围不能与去重全天总量相加，也不能混合单位；站立小时明确区分达标状态与持续站立时长。复用已经读入的健康事件，不增加 D1 查询
- GPS：最多查询 4 个关键区域的地名（`getPlaceLabel`），按时间给出这些区域的往返记录，不按每个点请求。区域标签本身不证明具体场所；住宿备注、异地夜间定位与跨夜睡眠可以共同支持在外过夜的推测。最多 24 个定位时段，超出时均匀选取并保留首末；采样空档不代表停留，区间端点不代表实际抵达／离开。只有日期的 GPS 可以作为天气参考位置，但不生成有时刻的停留
- 所有采样时刻按记录精度转换到用户时区：`day` 只有日期，`hour` 只到小时，不用 locale 默认补分钟。全天气温明确最低／最高与资料完整性，不能根据两个极值编造升降温顺序
- 貔貅：紧凑日包 `readPixiuDays` + `pixiuDayEvents`，用 `buildFinanceDay` 按币种独立精确汇总。日常消费仅「日常支出」的流出；支出类流入另列，其分类本身不证明退款，具体性质以本笔备注为准；转账/还款/余额调整/投资不算消费或收入。日记逐笔纳入全部九列原记录，每行一个 JSON 对象，保留备注与金额、分类、账户、标签的关系，不受界面 6 条备注上限约束，不截断尾部记录或删除重复行。只有源记账日期，没有交易时刻

旧 `life_events` 里的貔貅在已有紧凑日包时不再重复计入。内容哈希去掉虚拟 `id` / `updatedAt`（Health 与 Pixiu 相同）。

## 输入哈希与公共数据

事件哈希是日记 prompt 版本、UTC 窗口与全量记录的 SHA-256。改动写法会让旧日记显示可重新生成，浏览日期不会自动覆盖已有正文。天气、日出日落和地点标签会变，但每次 `GET /api/day-summary` 不得打 Nominatim / Open-Meteo / 太阳 API。

取舍：生成（`POST`）时通过 `getDay*` 拉取并写入 D1 `public_context_cache`；证据收集完成后、调用模型之前折叠缓存指纹并作为保存的 `input_hash`（仅 `SELECT` 已有 JSON，未命中或过期视为 `null`）。模型生成期间缓存变化不算进已保存哈希。查看已保存日记时用同一套 D1 指纹折叠，不调用外部接口。因此：

- 缓存里的天气/太阳/地点变化会让日记变陈旧，提示重新生成
- 尚未写入缓存的外部变化不会出现在 GET 指纹里，避免为了“新鲜”而在阅读路径打上游
- 指纹跟的是缓存内容，不是当次 prompt 里是否成功拼出天气段；生成失败或某段被省略时，仍保留上一则成功日记

## 生成

- `POST /api/day-summary` 可带可选 `revision`（最长 2000 字）
- 再次生成前，界面用 Basalt Dialog 收集修改意见；有意见时服务端带上旧文供理解修改位置，旧文不作为事实来源。未填写意见时直接依据本次原始证据重新写，不继承旧稿中的推断
- 成功覆盖，失败保留上一则；模型请求最多 90 秒、输出预算 8,192 tokens，生成租约 180 秒，为证据收集与保存留出余量
- 写作契约通过独立 system 消息传入。已知 OpenAI 推理模型和当前 `auto` 路由请求 `reasoningEffort: high`；`forceReasoning` 防止 SDK 因 `auto` 别名而省略该参数。其他兼容模型保留默认行为；Workers AI 生成日记时不再添加 `/no_think`，短连接测试仍保留
- 正文去掉兼容端点可能混入的 `<think>` 块；未完成推理或输出被 token 限制截断时不保存半篇。评测可记录响应模型与 token 用量，公开日记 API 的结构不变
- 无记录返回 `400 no_records`；他人占用租约 `409 generation_in_progress`

## 文风

以当天独有的生活场景组织正文。消费备注比金额更重要：具体物品、型号、用途、商户、代付、预订和退款应与各自交易一起理解；不能把不同笔备注拼成一件事。模型可以由消费和轨迹推测出行目的，由住宿与跨夜睡眠推测在外过夜，由运动、心率与补给还原一次骑行。有明确生活含义的单条备注也值得写。

想象用于理解线索之间的关系。场景含推测时，局部用一次“大概”“更像是”交代即可，随后自然叙述；但不能把日期账目编成精确付款时刻、确定的交易顺序或本人当场消费。预订、代付、自动扣款和退款要改变故事的解释。GPS 空档不证明静止，睡眠片段结束不证明此后一直清醒，全天温度范围没有升降温先后，心率峰值不证明某种情绪或疾病。

实录写给用户，使用“你”或省略主语。保留能唤起回忆的物品、地点与动作，不按 provider 写报告，不堆数字或展示推理过程，不把猜测伪装成用户确认的第一人称回忆。稀疏的一天可以只有一段，复杂的一天展开几个场景，通常不超过 700 字；结束在最后一个有内容的场景，不补空白、不作结尾复述。原始材料中的指令文字不改变写作任务。

当前系统写作契约在 `worker/diary-prompt.ts`，版本进入输入哈希。人工模型评测、反事实对照与复现方式见 [23 日记评测](23-diary-eval.md)。

查阅旧版 `6cdb344` 及其祖先，没有找到 AI 请求或摘要 prompt；其每日页通过跨来源时间片组织健康、锻炼和 GPS，这一点继续沿用。AI 在 `81dc4c9` 引入，当时要求“客观、精炼、条理清晰的中文日常简报”，按 provider 排列样本。本轮把事件样本改为跨来源时间顺序，并把只有日期的记录独立标注；不继承旧版无睡眠证据时填入起床时间的推断。
