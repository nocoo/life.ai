# 貔貅记账：按日存储分析

2026-09-14 原始分析。用户随后明确所有貔貅日期均为 UTC+8 记账日；最终实现与导入核验见 [完整日包与每日账目](22-pixiu-daily-import.md)。以下空间对比保留分析阶段的实测口径。

建议每个有流水的来源记账日存一条完整 JSON，以 provider 与来源日期唯一标识。当天的所有原始流水放在正文，分类统计放在同一行的 `summary_json`；保留明细，减少物理行和重复字段名。最终复用 `provider_days`，按用户确认的 UTC+8 映射账期，技术日期键与实际 UTC 范围分开。

| 2021.csv | 162 | 121 | 2021-01-07 — 2021-12-28 |
| 2022.csv | 1,198 | 295 | 2022-01-07 — 2022-12-31 |
| 2023.csv | 1,855 | 351 | 2023-01-01 — 2023-12-31 |
| 2024.csv | 2,031 | 365 | 2024-01-01 — 2024-12-31 |

| 2026.csv | 1,585 | 257 | 2026-01-01 — 2026-09-14 |
| 合计 | **8,690** | **1,832** | 2020-01-12 — 2026-09-14 |

九个字段完全一致：`日期`、`交易分类`、`交易类型`、`流入金额`、`流出金额`、`币种`、`资金账户`、`标签`、`备注`。所有日期均为 `YYYY-MM-DD`，没有时分、时区或交易 ID。701 条流水的字段含逗号，必须使用 CSV 解析器，不能按逗号直接切分。

CSV 本身没有时区标记；来源日期按用户确认的 UTC+8 解释，保留 `Asia/Shanghai` 和固定偏移 480 分钟。这属于用户确认的日期规则，并非 CSV 自带字段。

每日平均 4.743 笔，中位数 4 笔，P95 为 12 笔，最多 28 笔。日期范围内有 606 天未提供流水，不推断为遗漏或零消费，也不为空白日期创建数据行。

## 完整性与金额语义

- 全部 17,380 个金额字段都有两位小数，无负数字面值。133 条流水的流入、流出均为零，仍保留其分类、账户、标签和备注。
- 存在 87 组九个字段完全相同的流水，包含 99 次额外重复，最高重数为 5。无法证明这些是错误重复，必须全部保留。幂等作用于整日快照，不能对流水做 `DISTINCT`。
- 原始交易分类有 21 种，交易类型有 162 种。7,281 笔属于“日常支出”，611 笔属于“日常收入”，另有 798 笔属于还款、余额调整、赎回、保费、预付、报销、兑换等分类。
- “日常支出”中有 13 笔流入，可能涉及退款或冲销；不能仅凭金额方向改写为收入。基金赎回、理财赎回等也包含不同方向，保留原始分类和流入、流出两列。
- 币种为人民币 8,659 笔、港币 7 笔、美元 24 笔。分币种汇总；导出中没有汇率或完整的兑换对应关系，不能直接合并总额。
- 不根据同日、同额自动合并转账的两端。导出缺少可靠关联 ID；账户流水数与经济交易次数需要区分。

原始金额以字符串保存，包括 `0.00`。汇总时用十进制字符串精确转换为最小货币单位的整数，禁止使用浮点累加。当前全部分类汇总均通过 JavaScript 安全整数范围校验；未来越界或出现不同小数位时应明确处理，不能静默截断。

`summary_json` 建议先记录“币种 × 原始交易分类”的条数、流入分值、流出分值，避免在存储层把所有资金流动压成“收入/支出”。消费、退款、转账、资产变动的展示规则应另行明确。

## 三种存储方案的本地实测

使用项目当前四份迁移创建独立 SQLite 文件，保留现有索引与统计触发器。逐笔方案模拟当前事件字段、正文和外部键；按日方案复用 `provider_days`。各方案扣除相同的 151,552 bytes 空表与来源元数据基线。以下是新增空间估算，**不是生产 D1 的实测增量**；生产页布局、已有空闲页和运维元数据会影响实际大小。

| 方案 | 内容行数 | JSON 正文 | 日汇总 | SQLite 新增空间 |
| --- | ---: | ---: | ---: | ---: |
| 每笔一个事件，九字段对象 | 8,690 | 2,058,581 B | — | 6,324,224 B / 6.031 MiB |
| 每日一行，内含对象数组 | 1,832 | 2,135,055 B | 161,838 B | 3,190,784 B / 3.043 MiB |
| **每日一行，字段表 + 行数组** | **1,832** | **1,390,305 B** | **161,838 B** | **2,121,728 B / 2.023 MiB** |

推荐第三种：相比逐笔方案，内容行减少 **78.92%**，本地新增空间减少 **66.45%**。`dataRows` 为 1,832，实际账目 `recordCount` 仍为 8,690；来源状态和导入会话另有少量固定管理行。

推荐方案的单日正文与汇总合计平均 847 B、中位数 711 B、P95 1,802 B、最大 **4,472 B / 4.37 KiB**。D1 当前单行上限为 **2,000,000 bytes**，本批数据完全不需要拆日或拆维度。

结构示例（合成数据）：

```json
{
  "v": 1,
  "precision": "day",
  "columns": ["日期", "交易分类", "交易类型", "流入金额", "流出金额", "币种", "资金账户", "标签", "备注"],
  "rows": [
    ["2026-09-14", "日常支出", "早餐", "0.00", "18.00", "人民币", "现金", "", ""]
  ]
}
```

表头每个日期只写一次；各单元格及同日原始行顺序保留。版本化 codec 负责把行数组还原为带字段名的对象。原始 CSV 保留在本机，JSON 保存完整单元格内容，不承诺重建 CSV 的引号、换行编码等字节形式。

实测所有方案均通过 SQLite `integrity_check`，还原后的 **78,210 个单元格**、流水重数及按币种/原始分类计算的精确金额合计一致；按日方案也验证了日内原始顺序。

## 读取与幂等

1. “每天”指来源记账日，保留原始日期、`precision: day` 和明确后的来源时区。只有明确时区后，才能将该日的起止边界转换为 UTC 用于范围比较；不能为每笔日期型流水补造一个零点时间。若采用 `Asia/Shanghai`，`2026-09-14` 的日范围为 `[2026-09-13T16:00:00Z, 2026-09-14T16:00:00Z)`，不是 UTC 9 月 14 日零点。来源日仍整体保存一行，不机械拆成两个 UTC 日。现有 `utc_day` 是整 UTC 日分区键，复用时必须区分技术日期键和真实 UTC 范围，不能直接写入 UTC+8 日起点冒充整 UTC 日键。每日界面放到全天记账卡片，原始流水放记录 tab，不推测消费时刻或对应 GPS 点，也不把全天金额按时长分摊。
2. 每日视图通过 provider 与日期键索引读取对应来源记账日的一个内容行；需要汇总时只取 `summary_json`，打开原始记录时再解码当天完整流水。跨时区展示仍须保留来源记账日的语义，避免把同一份全天金额重复计入两个展示日。最多 28 笔的本批日数据适合直接解析，通常读取链路比 JSON 解析更值得关注。
3. 月度统计只读取日期范围内的日汇总，最多 31 个内容行。数据管理沿用 `provider_state` 的总量和版本化覆盖缓存，避免每次访问重扫所有流水。内容行数不等于 D1 最终计费的 `rows_read`，实际以返回的 `meta` 为准。
4. 同一日再次导入时整日替换，正文与汇总一起更新。先比较 `content_hash`，内容相同不重写；A → B → A 应恢复 A。哈希基于规范化的完整行多重集，包含重复次数，排除文件名、导入时间等会变动的元数据；仅调整导出行顺序不产生新的内容版本。
5. 本批年度文件的日期互不重叠。将来若同批文件覆盖同一天，应明确该日使用哪份完整快照，不直接叠加。按账户或分类筛选后的导出也不能被误认为完整日快照。
6. 默认仅替换输入中出现的日期，未出现日期保留。因此年度 CSV 不会删除其他年份；若删除了某天全部流水，必须通过明确的空日/完整范围替换语义清空，不能从文件里“没有出现”自行推断删除。

现有旧导入按流水内容生成键，修改一笔后可能留下旧事件；其日汇总主要按流入、流出直接相加，转账识别依赖“交易类型”文字。新的整日快照及原始分类汇总需要替换这两处路径，不能只把 JSON 打包后仍走旧导入 API。

## D1 费用

已查阅 Cloudflare 当前官方说明：

- [D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/)：Paid 每月包含 250 亿行读取、5,000 万行写入及账户合计 5 GB 存储；超额分别为 $0.001 / 百万行读取、$1 / 百万行写入、$0.75 / GB-month。
- [D1 Limits](https://developers.cloudflare.com/d1/platform/limits/)：单行上限 2,000,000 B，Paid 单库上限 10 GB；SQL 绑定参数每条最多 100 个。

只要账户仍有包内额度，本批数据不会产生额外的 D1 用量费用；其他数据库也共享账户额度。即使存储额度已经用完，推荐方案按本地新增空间折算也仅约 **$0.0016 / 月**。这是 D1 存储估算，不含 Workers 请求/CPU 等其他产品费用。

1,832 是内容行数，不是完整首次导入的计费写入数。现有日表每次插入还会更新主键索引和 `provider_state`，导入会话也有写入。本地 SQLite 记录到内容行加触发器共 3,664 次逻辑变化，此数不包括索引写入，不能直接当成 D1 账单；实际应在实现后累积每批 `meta.rows_read / rows_written` 验证。

这批账本的绝对体积较小。按日存储的主要价值是与每日阅读方式一致、固定覆盖更新边界，并降低长期索引和重复写入开销。
