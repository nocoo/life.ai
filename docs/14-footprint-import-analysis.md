# 14 Footprint GPX 导入与 D1 成本评估

分析日期：2026-09-14。本文件保留实施前的样本、候选结构和费用测量；已批准实现及生产核验见 [15](15-data-management.md)。其中 3,250 次写入仅为候选日包表及索引测量，不代表含统计触发器、会话回执的最终全量导入。

后续设计见 [15 数据管理与 Footprint 导入方案](15-data-management.md)。用户已明确：同一来源、同一 UTC 日由后一次导入整日替换；本报告初稿中的新旧点合并建议已被取代。存储测量数据保持不变，编码建议结合后续 Chrome 实测更新。

这份 GPS 数据适合按 **来源 + UTC 日** 打包，一行保留当天的全部轨迹点。现有结构全量导入约占 395–415 MB；普通 JSON 日包约占 80 MB，紧凑数组日包约占 29 MB。两种日包都是 1,625 行，不需要降采样，也不需要为了这份数据引入 R2。

当前建议采用紧凑 JSON 数组日包，在模型层解码后复用现有地图点结构。首轮考虑代码复用推荐普通对象；后续真实轨迹测量表明，最大 UTC 日的数组解析、解码和日视图分析约为 3.94 ms，普通对象为 3.06 ms，地图输出一致。这一开销结合用户对紧凑存储的偏好，支持选择约 29 MB 的数组方案。两者的 D1 行读写成本相同。其他 provider 的存储粒度等各自样本分析完成后再确定。

本次完整读取原始文件，并在临时本地 SQLite 和隔离的 Miniflare D1 中测量。没有向生产导入，没有修改应用代码、数据库迁移或 Cloudflare 配置。

| 字段 | 实际格式 | 处理含义 |
| --- | --- | --- |
| `lat` / `lon` | 全部为 8 位小数 | 保留原有数值，不把显示用的小数位数写回原始点；小数位数不代表实际定位准确度 |

| `extensions/course` | 全部为 2 位小数 | 扩展字段，文件没有单位声明；保留原值，派生指标需明确无效值规则 |

全部点都有上述字段，经纬度均为有效数值并位于合法范围。没有其他轨迹点字段，没有 `rtept` 或 `wpt`。速度与方向字段沿用 GPX 默认命名空间，没有另设厂商扩展命名空间。

## 存储方案比较

所有日包方案都保留 670,191 个点及时间、经纬度、海拔、速度、方向，不做降采样或坐标舍入。日包另含点数、首末时间、24 小时点数摘要和内容哈希。这里的“保留”针对点和数值，原始 XML 的空白、字符串格式及文件顺序仍以原文件为准。

| 方案 | D1 数据行 | 本地 SQLite 总占用 | 最大日包正文 | 取舍 |
| --- | ---: | ---: | ---: | --- |
| 当前通用事件，一点一行 | 670,191 | 394.57–415.47 MB | 不适用 | 索引和重复元数据多；直接 SQL 查单点方便 |
| UTC 日包，普通 JSON 对象 | 1,625 | 80.30 MB | 417,544 bytes | 字段清楚，易于复用现有地图对象结构 |
| **UTC 日包，紧凑 JSON 数组** | **1,625** | **29.29 MB** | **148,809 bytes** | 当前建议；字段名单放包头，每点保存六个数值，模型层统一编解码 |
| UTC 日包，gzip 后存 BLOB | 1,625 | 正文合计 9.43 MB；未实测完整 SQLite 文件 | 52,681 bytes | 数字仅为紧凑数组 gzip 正文；增加解压与调试成本，SQL 无法直接读取内部字段 |
| D1 日索引 + R2 日包 | D1 约 1,625，另有 R2 对象 | 取决于摘要；原始日包移到 R2 | R2 不受 D1 单行上限约束 | 本样本无需这一层；适用于后续确实很大的原始数据 |

普通 JSON 日包把数据行减少约 **412 倍**，存储较整理后的当前结构减少约 **79.65%**。紧凑数组存储减少约 **92.58%**，其正文日均 17.07 KB、中位 14.13 KB、P95 40.23 KB。

普通 JSON 使用对象数组，点字段为 `time, latitude, longitude, elevation, speed, course`；紧凑数组把时间改成距 UTC 日起点的秒数，字段顺序在包头声明。二者保存相同的业务数值。数组表示节省字段名和重复日期字符串，并不减少点。

按小时保存也是可行方案：本样本会产生 9,189 个非空小时包。但每日视图通常需要整天轨迹，且最大日包已经很小，这份数据没有必要强制拆成小时行。没有记录的小时由时间线展示空档，不为其建立空数据行。

## 读取成本：必须配套处理当前查询

[来源列表](../worker/routes.ts) 每次通过 `COUNT(e.id)` 和 `MAX(e.occurred_at)` 聚合所有原始事件。[时间线 ViewModel](../src/viewmodels/timeline-view-model.ts) 每次加载日期都会请求该列表，所以不能把一天约 412 个点当成打开页面的总读取量。

当前事件查询为了同时支持点事件与跨日区间，使用范围条件和区间条件的 `OR`。在全量副本上执行 `EXPLAIN QUERY PLAN`，首页和带游标分页均出现：

```text
SCAN e USING INDEX idx_life_events_range
```

这是沿时间索引扫描，并未用所选日期的下界直接定位。来源过滤只把扫描范围收窄到该来源，并未解决来源内的全历史扫描。单独的点时间范围查询则能使用：

```text
SEARCH life_events USING INDEX idx_life_events_range (occurred_at>? AND occurred_at<?)
```

另外在本地 Miniflare 构造 10,001 条不含真实位置的合成事件，用同样查询验证计量：

| 查询 | 返回记录 | `rows_read` |
| --- | ---: | ---: |
| 当前事件查询，读取接近末尾的一天 | 24 | 10,025 |
| 可使用时间范围的点查询，同一天 | 24 | 48 |
| 当前来源列表汇总 | 1 个来源 | 10,003 |

以上计量含查询中的来源表访问，不应当按返回 24 行计费。当前 AI 摘要新鲜度检查也会分页读当天事件并计算哈希，采用相同的区间条件；生成时还会再次校验。

以一次扫描约 67 万行为例，1,000 次此类查询约为 6.7 亿次行读；即使 Paid 读取额度已经用完，边际费用也约为 $0.67。真正需要改善的是反复扫描、分页和 Free 的每日额度消耗。拥有 Paid 剩余额度时仍不产生这部分额外读费用。

日包方案需要同时做到：日期读取命中 `(source_id, utc_day)`；来源统计依据日包的点数/首末时间字段；地图按需要读取当日数据；AI 在选定本地日的 UTC 窗口内处理材料。若继续在打开页面时扫描旧的全部 `life_events`，只增加日汇总表并不能解决这些读取问题。

## 拟议存储和导入规则

GPS 的候选行结构如下，表示设计方向，并非待执行迁移：

```text
source_id       来源，当前为 footprint
utc_day         UTC 零点的 epoch 时间，与项目统一使用毫秒
point_count     原始点数
first_at        本包首个点的 UTC 时间
last_at         本包最后点的 UTC 时间
summary_json    24 小时摘要、数据质量统计等派生信息
data_json       { v: 1, fields: [...], points: [[offsetSeconds, lat, lon, ele, speed, course], ...] }
content_hash    规范化并排序后的内容哈希
updated_at     内容确实改变时才更新
PRIMARY KEY (source_id, utc_day)
```

实际测量的日包表将首末时间放在 `summary_json`；拆成两个数值列只会增加少量元数据。表名和与其他 provider 的共享方式待下一批原始数据分析后确定，不预先要求所有 provider 都套同一种 payload。

1. **存储按 UTC 日，点保持秒级精度。** 日包是存储容器，不是 `precision=day` 的日级事件。读取上海 2026-09-14 应用的窗口为 `[2026-09-13T16:00:00Z, 2026-09-14T16:00:00Z)`；取覆盖该窗口的 UTC 日包，拼接排序，再按半开区间裁切。一般需一至两个 UTC 日包，应按真实时区窗口求交而非写死数量。
2. **保留每日地图和 24 小时故事线。** 由包内点恢复小时轨迹、地图、原始点列表和派生指标；不把一整天浓缩成一个无法展开的摘要。缺失记录区间保持未知，不能据此推断静止或零活动。跨包边界的连续性和距离计算需有明确规则，不能把窗外点误算到本日。
3. **重叠日期整日替换，再以当前哈希判断是否需要写入。** 按用户后续明确的规则，同一天的新文件内容覆盖旧日包；即使新文件只包含该日部分轨迹，也不与旧点合并。文件未包含的日期保留。同一文件内乱序出现的同日点要完整归并，同时间戳的不同点不能静默丢失。A → B → A 必须恢复 A，不能因文件曾经导入过就跳过。详见 [15 的覆盖规则](15-data-management.md)。
4. **未变化的日期零写入。** 使用哈希比较或带 `WHERE old_hash != new_hash` 的条件 upsert。当前 SQL 每次重导都会更新 `updated_at`，而 AI 输入哈希包含它，因此相同内容也会导致摘要被判陈旧；日包需避免这种无意义变化。AI 证据和最终输入哈希仍以裁切后的本地日窗口为准。
5. **按实际字节控制大小。** 当前最大普通 JSON 日包约 418 KB，所有日期都低于 512 KiB，可以一日一行。建议 GPS 日包使用专门的大小校验和按字节组批；未来遇到超过预算的日包再明确分片，保留完整时间覆盖，不能截断点。
6. **不能直接沿用当前 32 KiB 的单条限制。** 普通对象日包有 1,051 日超过此限制，紧凑数组也有 170 日超过。现有接口整体上限为 1 MiB，客户端目标批大小为 512 KiB；后续实现需同步设计 GPS 日包契约与组批，不是简单把 `points` 塞进当前事件 `data` 即可。Connect 的小时快照语义与 GPS 存储分包分别处理。
7. **继续流式读取原档。** 当前解析器按 64 KiB 读取 GPX 的方向正确；归并过程要处理乱序，避免在 Worker 中一次性装入整个 160 MB XML。仅上传归并后的、大小受限的日包；原始文件留作恢复依据，若需要云端原档再接私有 R2。

紧凑 JSON 日包将这份数据降到约 29 MB、1,625 行，并保留现有每日地图需要的完整点。[15](15-data-management.md) 进一步定义数据管理页面、网页与本机共用的导入模块，以及整日替换、读取和旧数据切换的实施方案。
